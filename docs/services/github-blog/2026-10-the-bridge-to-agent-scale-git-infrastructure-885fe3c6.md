# The bridge to agent-scale Git infrastructure

> GitHub Blog · 2026-10-21 · Architecture &amp; optimization

---

지난해 GitHub는 에이전트 트래픽 급증과 데이터센터 전력·공급 제약에 대응해 저장소의 대부분을 Azure로 옮겼고, 현재는 대다수 저장소가 두 장소에 복제되어 운영되고 있다. 남아 있는 극소수(0.00001%)의 가장 바쁜 리포지토리는 지역 간 왕복 지연(약 25ms) 때문에 쓰기 처리량 한계에 묶였는데, 기존 설계는 리포지토리 전체에 걸쳐 하나의 직렬화된 락을 유지하면서 가장 느린 정상 복제본이 전체 쓰기 지연을 결정했다. 이를 해결하기 위해 GitHub는 조율을 최소화하고 스토리지를 컴퓨트에서 분리한다는 원칙 아래, 쿼럼의 범위를 리포지토리 전체에서 개별 레퍼런스 단위로 좁히는 변화를 도입했다. 대부분의 푸시는 서로 다른 레퍼런스를 건드리기 때문에 레퍼런스 단위 직렬화는 별개의 쓰기들이 동시에 진행되도록 허용해 저장소 단일 병목을 제거하고, 내부 테스트에서는 서로 다른 레퍼런스에 대한 쓰기 처리량이 3~4배 향상되며 지연도 낮아졌다고 보고한다.
읽기 확장에는 오브젝트 스토리지를 쿼럼의 특별한 멤버인 '가상 복제본(virtual replica)'로 포함시키는 접근을 도입했다. 가상 쓰기 복제본은 영속성을 갖춘 오브젝트 스토리지에 쓰기를 스트리밍하면서 읽기를 제공하지 않는 완전한 일시적 노드로 동작해, 쓰기 인정 시점에 데이터가 오브젝트 스토리지에 영구화되도록 보장한다. 이 방식은 쓰기당 약간의 추가 지연을 더하지만 레퍼런스 단위 직렬화와 결합해 병목이 되는 것을 막고, 여러 동시 쓰기를 하나의 I/O로 합쳐 비용을 줄인다. 이후 가상 읽기 복제본을 필요에 따라 확장하여 오브젝트 스토리지를 진실의 원천으로 삼고 각 복제본이 백그라운드로 상태를 조정하면서 읽기 부하를 독립적으로 처리하게 할 수 있다. 다만 초기 가상 읽기 복제본은 백그라운드 동기화 방식이므로 모든 읽기 워크로드에 바로 적합하지 않고, 쓰기 처리량을 더 끌어올리려면 아직 남아 있는 쿼럼 관련 경계와 레퍼런스 상태의 영속 위치, 컴팩션·가비지 컬렉션 같은 2차 문제들을 해결해야 한다는 점을 저자는 명확히 밝히고 있다. 이러한 단계적 변화는 에이전트 중심의 트래픽 증가에 대응해 저장소 운영의 유연성과 확장성을 실질적으로 끌어올리는 중요한 전환으로 보인다.
