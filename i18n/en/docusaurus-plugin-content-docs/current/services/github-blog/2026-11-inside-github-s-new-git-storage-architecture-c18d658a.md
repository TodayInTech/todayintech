# Inside GitHub’s new Git storage architecture

> GitHub Blog · 2026-11-05 · Git 인프라

---

지난주 GitHub Universe에서 공개된 **Project Rubicon**은 한 리포지토리에서의 수직적(단일 리포지토리) 확장을 목표로 설계된 새 Git 저장소 아키텍처다. 내부 테스트에서 **5,000개의 동시 에이전트**가 하나의 리포지토리를 작업하고 **초당 7,200개의 푸시**를 보낼 수 있음을 입증했다고 GitHub는 밝혔다.

## 아키텍처 핵심 — 저장과 실행의 분리

Rubicon은 두 가지 설계 원칙을 따른다: 조율 최소화와 저장소와 컴퓨트의 분리. 구체적으로 팩과 읽기 가속 데이터는 **Azure Blob Storage**에 저장하고, 참조와 리포지터리를 구성하는 팩 목록(팩 매니페스트)은 **Ref-CAS(Reference Compare-and-Swap)**라는 별도 복제 로그 서비스에 둔다. 이 분리는 대용량 쓰기와 다수의 읽기가 동시에 발생할 때에도 각 요소를 독립적으로 확장하게 한다.

## 가상 레플리카(virtual replicas)와 Spokes

요청은 Spokes를 통해 리포지토리에 할당된 소수의 가상 레플리카로 라우팅된다. 가상 레플리카는 읽기·쓰기·혼합 처리를 담당하며 로컬 디스크는 재구성 가능한 캐시 역할을 한다. 레플리카는 교체 가능하며, 리포지토리가 바쁠 때는 레플리카를 추가해 처리량을 높인다. 가상 레플리카는 푸시에서 팩을 인덱싱해 Blob Storage에 업로드한 뒤 Ref-CAS에 한 건의 트랜잭션으로 팩 매니페스트와 참조를 갱신한다.

## Ref-CAS: 참조 상태만을 위한 복제 로그

참조(reference) 업데이트만 합의가 필요하다는 관찰을 바탕으로 GitHub는 참조 전용의 복제 로그인 Ref-CAS를 도입했다. 각 참조 갱신은 LSN(log sequence number)을 받고, 트랜잭션은 갱신 대상 참조만 잠그고 비교-교체(compare-and-swap)를 수행해 과도한 조율을 피한다. 가상 레플리카는 자신이 가진 버전과 Ref-CAS의 버전을 비교해 변경이 없으면 네트워크 비용이 거의 들지 않게 읽기를 완료한다.

## 컴팩션: 별도 노드에서의 샤드 기반 처리

모든 푸시는 Blob Storage에 새로운 팩을 추가하기 때문에 팩 수가 늘어나면 읽기 비용이 커진다. Rubicon은 컴팩션을 트래픽을 서비스하는 레플리카에서 떼어내어 **전용 컴팩션 노드**가 Blob Storage와 Ref-CAS를 직접 사용해 처리하도록 했다. 각 컴팩션 노드는 샤드에 대해 리스(lease)를 획득해 독점적으로 작업하고, 입력 팩을 모아 더 큰 팩으로 병합한 후 매니페스트를 원자적으로 갱신한다. 병합과정에서 객체의 보존을 확인하고, 입력을 제거하는 두 단계 트랜잭션으로 일관성을 유지한다.

## 왜 중요한가(실무적 의미)

이 아키텍처는 **참조 상태만을 신속히 직렬화**하고, **팩 데이터의 불변성**을 활용해 Blob Storage의 고처리량을 끌어쓰는 방식으로 고빈도 병렬 푸시를 견디도록 고안됐다. 결과적으로 읽기 지연을 낮게 유지하면서 수천 건/초의 쓰기를 처리할 수 있고, 컴퓨트(레플리카)와 유지관리(컴팩션)를 독립적으로 확장할 수 있다. 또한 GitHub는 기존 레거시 스택에서 리포지토리들을 Azure로 마이그레이션(문서에선 **99.99999%** 수치 언급)한 뒤 이 설계를 깔아 운영 중이라고 밝혔다.

## 이후 계획(원문 근거)

GitHub는 추가 최적화로 "필요한 객체만 읽기", 팩을 유형별로 분류, 부분 레플리카, 물질화된 뷰, 지역별 글로벌 레플리카, 활동에 따른 스케일 투 제로 등을 제시했다. 이들 개선은 읽기 비용을 더 줄이고 에이전트 중심 작업에 맞춘 효율성을 높이는 방향이다.

이 보도는 GitHub의 기술 블로그(작성자 Karthik Raman)의 설명을 근거로 정리했으며, 아키텍처의 주요 수치와 설계 요소는 제공된 원문 근거(chunk-0001~0003)에 따라 서술했습니다.
